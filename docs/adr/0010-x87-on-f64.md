# ADR 0010 — x87 floating point is modelled on `f64`

Status: Accepted (2026-11-20)

## Context

The x87 unit computes in an 80-bit format that neither Rust nor WebAssembly
has. Emulating it in software is slow; ignoring it changes results. The
browser is the first target, so "use the host's 80-bit type" is not available.

## Decision

Registers hold `f64`. The precision-control and rounding-control fields of the
control word are honoured:

- double precision (the C runtime's default): plain `f64` arithmetic;
- single precision (what Direct3D 6 selects): the `f64` result is rounded
  again to 24 bits, keeping the wide exponent range. This is exact, because
  53 >= 2 * 24 + 2 makes the double rounding harmless;
- directed rounding modes: the nearest result is corrected by one unit in the
  last place using the sign of the exact rounding error (two-sum, fused
  multiply-add), so `+ - * / sqrt`, stores and integer conversions are
  correctly rounded in all four modes.

## What is not exact

- Extended precision (64-bit mantissa). The interpreter raises a diagnostic
  flag if code ever computes with it selected. Whether the game does is
  `UNVERIFIED` until it runs.
- Transcendental functions (`fsin`, `fcos`, `fptan`, `fpatan`, `fyl2x`,
  `f2xm1`): as accurate as the host's maths library, last-digit differences
  from the hardware. They are deterministic for one build of the port, which
  is what replays need; cross-platform determinism will need a fixed
  implementation of these functions (open point for Phase 2).
- Integers above 2^53 loaded with `fild`, values outside the `f64` range, and
  `fprem` on operands more than 2^63 apart.
- `fnsave`/`frstor`/`fnstenv`/`fldenv` (six sites, in runtime error handling)
  are not implemented yet and trap.

## Consequences

- Results match the original bit for bit wherever the model is exact, without
  a software floating-point emulator.
- The same model compiles to WebAssembly unchanged.
